Hunt-Notes

I would like to create a db and app for my hunting exploits, and try to improve over my current manual notetaking that lives on old hunting regs and guides, so I can store info without losing it or having to re-highlight or re-enter my notes.  I think this app can serve as my hunting dashboard, so I don't miss dates and opportunities for drawings, tags, etc.  Also having the db will allow me to integrate data from different sources and quickly research hunting areas.

I would like to set it up on the same server as the commodities app and use the same db technology with SQLLite, which has been working well.

For the home tab, I'd like to put the important dates for drawings, seasons, by game.  On the top section, include the main dates for primary and secondary draw, and the seasonal dates, like the columns on page 2 of the hunting guide.  So Lets have columns for Deer, Elk, Pronghorn, we can leave moose and bear out.  Also add colums for small game including rabbit, dove, blue grouse, sage grouse, sharp-tail grouse and pheasant.  For each small game, include the hunting seasons, bag and possession.  

Stack: same as the commodities app — Express + better-sqlite3 backend, React/TS/Vite frontend, dark theme to match. Backend on port 4100, frontend dev server on 5180 (proxies /api).

Run it:
cd hunt-notes && npm install && npm run db:init && npm run dev     # backend
cd hunt-notes/frontend && npm install && npm run dev               # frontend

Quick clarification before I build this — Colorado's draw rule is one application per species per draw per year, and CPW treats "Deer" as a single species for that purpose (mule deer vs. whitetail is just which GMU/hunt code you pick within that one deer application, not two separate applications). Since My Hunt will track actual applications, I want to make sure the data model matches reality rather than implying you can file two deer applications.

What's there

Same column layout as Home (Deer | Elk | Pronghorn), fully editable, autosaves as you type (debounced, with a "Saving…/Saved" indicator next to each species header):

- Target This Year / Applied — checkboxes
- Primary Draw — Choice 1 & 2 hunt codes, a Draw Result dropdown (Pending/Drawn/Not Drawn), and the Hunt Code Drawn
- Secondary Draw — same shape, single choice field
- Leftover License — hunt code, Purchased checkbox, purchase date, and a notes field
- General Notes — freeform per species

A year selector (‹ 2027 ›) sits top-right, defaulting to 2027 since 2026's draw windows have already closed — you can page back to 2026 to log what actually happened this year if you want a record of it.

Design calls worth knowing about

1. Deer is one combined row, not split into Mule Deer/Whitetail — per your answer, since CPW only allows one deer application per year regardless of which GMU you target.
2. Nothing is pre-seeded. Rows only get created in the DB when you actually type something, so re-running npm run db:init later (e.g. after a future schema change) can never wipe your entries — it's structurally separate from the brochure data's destructive refresh.
3. No "Save" button — every field saves itself ~500ms after you stop typing. I verified this with a scripted browser test (filled every Elk field, confirmed "Saved," reloaded, confirmed the row was still in SQLite).
4. One known rough edge: there's no URL routing yet, so a full page reload always lands back on the Home tab (your saved data isn't affected, just which tab is showing). Easy to fix later if it bugs you.

What changed, and why

Your domain knowledge caught a real gap: Primary Draw and Secondary Draw were correctly singular (CPW really does cap those at one license per species per draw), but Leftover License was also locked to a single entry — which can't represent your actual 2026 example (a drawn archery tag D-F-103-O3-A plus a separately-purchased leftover rifle tag D-E-109-O2-R in the adjacent unit, both for Deer, same year — legal under List A/B).

Fixed by making Leftover its own list:
- Leftover/OTC Tags is now a repeatable set of cards per species — Hunt Code, Purchase Date, Notes, and a remove button — with "+ Add Leftover Tag" to add more. No cap on how many.
- Backend got its own table (MyHuntLeftoverPurchases) and CRUD endpoints, decoupled from the single-valued MyHuntPlans row.
- Since this changed the shape of an already-created table, I added a small guarded migration (checks column/table existence first) rather than just editing the schema — so it's safe whether you have existing data or not, and db:init stays idempotent.

I verified this against your exact example end-to-end (filled both tags, confirmed autosave, checked the API response directly) — did hit one real bug along the way (a flex-CSS issue collapsed the Hunt Code input to a sliver), caught it in the screenshot, and fixed it before pushing.

One thing I didn't change: Primary/Secondary Draw are still single-valued, since that matches the actual "one license per species per draw" rule.
